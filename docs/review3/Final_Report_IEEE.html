Abstract—Compilers for machine-learning workloads lose most of their optimisation opportunities when matrix programs are lowered too early to scalar code. We present MatrixDSL, a small domain-specific language for matrix and neural-network computation, and a complete compiler that lowers it to MDT (MatrixDSL Target), a 24-instruction matrix instruction set architecture (ISA) with 4×4 FP32 matrix registers and a 64 KiB software-managed scratchpad that we designed together with the compiler. The pipeline runs a hand-written lexer and parser, shape-as-type semantic analysis, lowering to a static single assignment (SSA) Tensor IR, three optimisation passes (use-count-guarded operator fusion with epilogue fusion, dead-code elimination and capacity-aware scratchpad tiling), MDT instruction selection, and execution on a simulator with an analytical performance model. We prove that the fusion rewrite, the zero-padding memory layout and the identity-tile addition are value-preserving, and we validate the implementation by differential testing against an independent reference interpreter: 100 of 100 compiled program variants and 70 of 70 regression tests pass. On eight workloads, fusion and tiling together reduce modelled cycles by a geometric mean of 2.19× and DRAM traffic by 3.79×. The two optimisations are super-additive on fused workloads. The evaluation also exposes a scratchpad capacity cliff at 128×128 and an ISA gap that prevents softmax from compiling to native MDT code. Source code, results and an interactive browser-based laboratory are public at https://github.com/shreyasmandem/MatrixDSL.

Index Terms—domain-specific languages, compilers, intermediate representations, operator fusion, loop tiling, scratchpad memory, instruction set architecture, differential testing, machine-learning accelerators.

I. Introduction

Deep-learning compilers such as XLA [1], TVM [2] and Triton [4] exist because general-purpose compilers discard the structure of tensor programs too early. Once a matrix multiplication has become nested loops in LLVM IR [6], the compiler can no longer see that a multiplication followed by a bias addition and an activation is one computation (an epilogue that can be fused [1]), nor that the same weight tile is fetched from memory dozens of times. Production accelerator stacks avoid both losses by keeping a tensor-level IR, fusing producer–consumer chains and staging data in software-managed on-chip memory, as the Tensor Processing Unit does [7].

MatrixDSL reproduces this design end to end, at a scale that a team of four students can build, read and measure within one course. The language makes the shape of every value part of its type, so dimension errors are compile-time errors. The compiler keeps matrix operations whole in a Tensor IR until the target-specific decisions have been made. The target, MDT, was specified in parallel so that every fused IR operation maps to an MDT instruction sequence.

The paper makes the following contributions:

  1. A complete, working compilation pipeline from MatrixDSL source to executed MDT code, built with only a C++17 compiler (≈9,600 lines across compiler, tools, tests and dashboard).
  2. A co-designed ISA. MATMULACC and MATMULRELU exist because the fusion pass emits exactly those patterns, and epilogue fusion of relu(A·B+C) needs no new opcode.
  3. Correctness arguments for the three rewrites the back end depends on (Section VI–VII). These are fusion soundness, the zero-padding invariant that lets ragged shapes run on a 4×4 unit, and exact matrix addition through the matrix unit's accumulate path.
  4. A verification method that makes compiled output bit-comparable with an oracle. It combines exact-arithmetic input generation with four-configuration differential testing [12], [13].
  5. A measured ablation study with three findings: super-additive fusion–tiling synergy, a scratchpad capacity cliff, and a concrete ISA gap.

II. Background and Related Work

A. Tensor Compilers and Intermediate Representations

XLA lowers whole TensorFlow graphs and fuses element-wise consumers into their producers. Snider and Liang [1] show that fusion accounts for much of its benefit. TVM [2] separates the algorithm from a schedule of loop transformations, a separation that Halide [3] introduced for image processing. Triton [4] exposes tiles as first-class values, and MLIR [5] provides a framework of dialects so that each level of abstraction can be optimised before lowering to LLVM [6]. MatrixDSL's Tensor IR plays the role of such a dialect: an SSA list of shape-typed matrix operations that sits between the AST and target code.

B. Accelerators and Software-Managed Memory

The TPU [7] pairs a systolic matrix unit with a large software-managed buffer whose contents the compiler, not a cache policy, decides. Blocking for reuse in a memory hierarchy is a classic compiler optimisation [8]. MDT adopts the same arrangement at teaching scale: eight 4×4 matrix registers, a 64 KiB scratchpad and DRAM.

C. Numeric Formats and Softmax

BF16 keeps FP32's exponent range with a shorter mantissa [9]. MDT supports it as a storage format. Numerically stable softmax subtracts the row maximum before exponentiation, and online normalisers [10] enable the softmax-epilogue fusion used by FlashAttention [11].

D. Compiler Testing

Differential testing compares implementations of the same specification [12]. Csmith [13] applied it to C compilers at scale. We apply it between the compiled MDT program and an independent reference interpreter, under four optimisation configurations.

IV. The MatrixDSL Language

A program is a sequence of declarations, assignments and print statements over FP32 matrices. Fig. 1 shows the grammar in EBNF. A tensor declaration with three bracketed dimensions adds a leading batch dimension. Matrix literals may contain signed decimal numbers.

program    ::= statement*
statement  ::= decl | IDENT "=" expr ";" | "print" "(" IDENT ")" ";"
decl       ::= ("matrix"|"tensor") IDENT ("[" INT "]"){2,3} ";"
expr       ::= term (("+"|"-") term)*
term       ::= factor ("*" factor)*
factor     ::= IDENT | NUMBER | literal | "(" expr ")"
             | ("matmul"|"transpose"|"relu"|"softmax") "(" args ")"
literal    ::= "[" row ("," row)* "]"     row ::= "[" ["-"]NUMBER ("," ["-"]NUMBER)* "]"

Fig. 1. MatrixDSL grammar (abridged).

The type of a value is its shape (b, r, c). Table IV gives the typing rules that the semantic analyser enforces. Batch broadcasting follows the familiar NumPy convention restricted to the leading dimension: batches must be equal, or one of them must be 1.

B. Lexical and Syntactic Analysis

The lexer is a hand-written scanner that tracks line and column for every token. Builtin names such as matmul and softmax are reserved keywords, not identifiers. The parser can therefore tell a call from a variable reference with one token of lookahead. The scanner distinguishes integer literals, which are used for dimensions, from floating-point literals, which are used for matrix elements, and rejects any other character with a positioned diagnostic. Table IV-a lists the token classes.

The parser is recursive descent with one function per grammar rule. Operator precedence falls out of the grammar's layering: expr handles additive operators, term handles *, and factor handles primaries. Both binary levels are left-associative. On a syntax error the parser records a diagnostic, then synchronises by skipping to the next ; and continuing (panic-mode recovery). A single missing semicolon therefore produces one error rather than a cascade. The parser builds the AST of Table IV-b, whose nodes carry source locations for later diagnostics.

C. Semantic Analysis

The semantic analyser is an AST visitor. It walks each statement in order, maintains a scoped symbol table that records each name's declared shape and declaration site, and computes a result type for every expression bottom-up using the rules of Table IV. The table also tracks whether each symbol is ever read, which yields the unused-variable warning. An expression whose operands are already ill-typed receives an invalid type that suppresses further messages, so one mistake produces one diagnostic. The * operator is resolved here: it is scalar multiplication when either operand is 1×1, and matrix multiplication otherwise. Table IV-c lists every diagnostic the analyser can produce.

VI. Tensor IR and Optimisation Passes

A. Lowering to SSA

Lowering walks the typed AST and appends one Tensor IR operation per expression node, each annotated with its shape. An assignment rebinds a name to the operation that computed its value rather than copying it. As a result, T = matmul(X,W); U = T + B; U = relu(U); lowers to the same graph as relu(matmul(X,W)+B), and named temporaries never block fusion. Observable behaviour is defined by print. A matrix read before it is ever assigned is a program input and becomes a Load operation.

Table VI-a lists the complete operation catalogue. Tier 1 operations correspond one-to-one with source constructs and are produced by lowering. Tier 2 operations are produced only by the passes. Most Tier 2 operations correspond to one MDT instruction or instruction pair, which is what co-design means in practice.

The intermediate names T and U have disappeared, so the fusion pass sees a single chain. This is the purpose of the chained_names test program.

B. Use-Count-Guarded Fusion

Table VI lists the fusion patterns. The Phase 3 addition is epilogue fusion: FusedMatMulAcc → Relu becomes a three-operand FusedMatMulRelu computing relu(A·B+C).

Table VIFusion Patterns

MatMul → ReluFusedMatMulRelu(A,B)MATMULRELU
MatMul → Add(C)FusedMatMulAcc(A,B,C)load C; MATMULACC

Proposition 1 (Fusion soundness): Let producer p feed consumer q with use(p) = 1. Replacing q by the fused operation computing q(p(x)) directly from p's operands, and deleting p, leaves the value of every Print unchanged.
Proof: Tensor IR is in SSA form, so every value is defined once and operations are pure. The fused operation computes, by definition, the same value q(p(x)) that q produced, so every user of q observes an identical value. The only value removed is p's result. Since use(p) = 1 and its single user was q, no remaining operation, and in particular no Print, reads it. Every printed value is therefore unchanged. If use(p) > 1, some other operation reads p, and deleting it would be incorrect. That is exactly the case the guard excludes.

The implementation is checked by a negative test (second_use.mtx) in which a matrix product is both printed and passed to relu. Fusion correctly does not fire.

C. Dead-Code Elimination

DCE marks every operation reachable backwards from a Print and erases the rest. Because operations are in SSA order, one reverse sweep reaches the fixed point. DCE removes the products that fusion absorbed.

D. Capacity-Aware Scratchpad Tiling

For a matrix-multiplication-family operation C(M×N) = A(M×K)·B(K×N), let Mt, Nt, Kt be the numbers of 4×4 tiles in each dimension. Each tile of A is read uA = Nt times and each tile of B uB = Mt times, multiplied by the batch count when the operand is broadcast. Algorithm 1 stages operands in the 64 KiB scratchpad.

Algorithm 1: Scratchpad tiling pass
  1. for each matmul-family op o in program order do
  2.   mark o TiledMatMul if MtNtKt > 1
  3.   candidates ← {operand x of o : ux ≥ 2}
  4.   sort candidates by saved bytes 64·tiles(x)·(ux − 1), descending
  5.   used ← 0
  6.   for each candidate x do
  7.     if used + 64·tiles(x) ≤ 65 536 then
  8.       insert ScratchStore(x) at offset used, then ScratchLoad
  9.       rewire o to read the ScratchLoad; used += 64·tiles(x)
  10.     else record "does not fit"
Proposition 2 (Staging profitability): Under the MDT latency model (DRAM load 8 cycles, scratchpad access 1 cycle), staging a tile read u times reduces its transfer cycles if and only if u ≥ 2.
Proof: Unstaged, the tile is loaded from DRAM at each use, costing 8u cycles. Staged, it is loaded once (8), stored to the scratchpad once (1) and read u times (u), costing 9 + u. Staging is cheaper iff 8u > 9 + u, i.e. 7u > 9, i.e. u > 9/7. Since u is an integer, this holds iff u ≥ 2.

The pass's decisions are visible with --stats. For matmul_32, it reports:

tiled matmuls        1
staged A of %6: 64 tiles, each reused 8x, saves 28672 DRAM bytes
staged B of %6: 64 tiles, each reused 8x, saves 28672 DRAM bytes

E. Case Study: Attention

The attention program of Fig. 1a exercises every pass, and it shows where the current passes stop. After lowering it has ten operations:

%0 = Load @Q : 16x16          %5 = ScalarMul %3 x0.25 : 16x16
%1 = Load @K : 16x16          %6 = Softmax %5 : 16x16
%2 = Transpose %1 : 16x16     %7 = Load @V : 16x16
%3 = MatMul %0 %2 : 16x16     %8 = MatMul %6 %7 : 16x16
%4 = Const : 1x1              %9 = Print %8 @O : 16x16

Fusion finds no pattern. %3 feeds a ScalarMul and %8 feeds the Print, neither of which is in Table VI. DCE removes the scale constant %4, which has been folded into the ScalarMul attribute. The tiling pass then finds that each 16×16 operand of each product has 16 tiles, each read 4 times. All four operands are staged: Q and Kᵀ at scratchpad offsets 0 and 1024, and the softmax output and V reusing the same offsets for the second product, because the scratchpad is free again after each consumer finishes. --stats reports four staging decisions of 3,072 DRAM bytes saved each. The softmax itself becomes one mdt_softmax runtime call. The measured result (Table XI) is a 1.36× speed-up from tiling alone. This case study is the origin of findings F4 and F5: a scale epilogue and a native softmax would let fusion contribute as well.

BF16 support. CVT.F32.BF16 keeps the upper 16 bits of an FP32 word (sign, the full 8-bit exponent and 7 mantissa bits) and CVT.BF16.F32 restores zeros in the lower half [9]. BF16 is a storage format only: all arithmetic remains FP32. The conversion is exact in the BF16 → FP32 direction. In the other direction it truncates, with a relative error below 2−7.

Simulator implementation. The assembler makes two passes over the source: the first records code and data labels, and the second decodes instructions and resolves symbols. The data section is built from the .float, .word and .space directives, and loaded at address 0. LOADT/STORET carry a row stride, so that a 4×4 tile can be read out of a wider row-major matrix. The simulator executes the decoded program instruction by instruction, checks every register class and memory access, and stops with a positioned runtime error on any violation.

B. Memory Layout and the Zero-Padding Invariant

Every DRAM-resident value receives one 64-byte-aligned buffer. The buffer is row-major, with rows and columns rounded up to multiples of four (r̂ = 4⌈r/4⌉, ĉ = 4⌈c/4⌉) and batches stacked. Tiles are read with strided loads (LOADT). Fig. 3 illustrates a 5×3 matrix.

Lemma 1 (Zero-padding invariant): If every input and constant buffer has zero padding, every buffer produced by the generated code has zero padding, and its real region holds the mathematically correct values.
Proof: Inputs and constants are emitted zero-padded. We consider each operation applied to zero-padded operands and examine the padding of its result (indices i ≥ r or j ≥ c). (i) Add/Sub: 0 ± 0 = 0. (ii) Scalar multiply: s·0 = 0. (iii) Transpose maps padding positions to padding positions. (iv) Relu: max(0,0) = 0. (v) Matrix product: Cij = Σk<K̂ AikBkj. For a padding row i ≥ M, every Aik = 0, and similarly for a padding column of B, so Cij = 0. For a real entry, the extra terms with k ≥ K have Aik = 0 and contribute nothing, so Cij equals the unpadded sum. Fused variants add a zero-padded bias and apply relu, preserving both properties. (vi) Softmax: the runtime normalises only the real c columns and writes zeros to all padding explicitly. By induction over the operations in SSA order, every buffer satisfies the invariant.

Lemma 2 (Exact addition through the matrix unit): With M7 = I, MATMULACC M0, M1, M7 sets M0 to M0 + M1 exactly in IEEE-754 FP32, and with M6 = −I to M0 − M1.
Proof: The instruction computes M0ij + Σk M1ik·Ikj. The product M1ik·Ikj equals M1ij exactly when k = j (multiplication by 1 is exact) and is a signed zero otherwise. Adding a zero to a finite value leaves it unchanged, so the partial sum is exactly M1ij and one correctly rounded addition gives fl(M0ij + M1ij), the IEEE sum. Replacing I by −I negates M1ij exactly.

Without this, MDT would add a tile with sixteen 4-lane vector instructions, each load paying the 8-cycle DRAM latency. The matrix unit does it in three instructions per tile.

D. Runtime ABI

MDT deliberately has no transcendental instruction and no I/O. mdt_softmax and mdt_print are host functions inside the simulator, reached by CALL with arguments in R1–R6. Softmax is charged 4 cycles and 8 DRAM bytes per element, and print is excluded from the model as host I/O. Table VII-c gives the calling convention. The generated code sets the arguments with ordinary ADD instructions, so a call's setup cost is counted like any other code.

VIII. Performance Model

The simulator records each executed instruction's latency ℓi and class (transfer, compute or other). The sequential estimate is

Tseq = Σi ℓi(1)

The trace is run-length encoded into maximal runs R1, …, Rm of one class with cycle sums t1, …, tm. Adjacent transfer/compute runs are paired left to right without overlap, and each pair costs the larger of the two:

Tovl = Σpaired (a,b) max(ta, tb) + Σunpaired c tc(2)
Proposition 3 (Bounds of the overlap estimate): ½ Tseq ≤ Tovl ≤ Tseq.
Proof: Each run appears in exactly one term of (2). For a pair, (ta + tb)/2 ≤ max(ta, tb) ≤ ta + tb. An unpaired run contributes its own tc, which lies between tc/2 and tc. Summing over all terms and using Σt = Tseq gives the result.

The model is analytical and is not cycle-accurate. It compares code-generation strategies on equal terms. It does not predict silicon.

A. Closed-Form Cost of a Tiled Product, and Validation

Because the generated code is straight-line and fully determined by the tile grid, its cost can be derived exactly. That derivation lets us check the simulator's accounting independently of the simulator.

Proposition 5 (Exact cost of a product): For a program computing and printing C = A·B with tile counts Mt, Nt, Kt (batch 1), let P = MtNt. The executed instruction count I, DRAM bytes D, scratchpad bytes S and sequential cycles T are, without staging,
I = P(3Kt+1) + 10, D = 64(2PKt + P), T = P(20Kt+8) + 10(3)

and, with both operands staged (U = MtKt + KtNt staged tiles),

I = 2U + P(3Kt+1) + 10, D = 64(U + P), S = 64(U + 2PKt), T = 9U + P(6Kt+8) + 10(4)
Proof: Unstaged, each of the P output tiles executes Kt pairs of DRAM loads (2·8 cycles, 128 B), Kt matrix-unit operations (4 cycles each) and one 8-cycle store. That gives 3Kt+1 instructions, 20Kt+8 cycles and 64(2Kt+1) DRAM bytes per tile. The constant 10 covers three base-address ADDs and the print call (six argument ADDs and one CALL, one cycle each), which move no DRAM data. With staging, each of the U staged tiles costs one DRAM load and one scratchpad store (2 instructions, 9 cycles, 64 B of DRAM and 64 B of scratchpad traffic). Every operand load in the product then becomes a 1-cycle scratchpad load, which changes the per-tile cycle count to 2Kt·1 + 4Kt + 8 and moves 2Kt·64 B of scratchpad traffic per tile. The base-address constant is unchanged: two staging bases and one result base replace the three operand and result bases. Summing over all tiles gives (3) and (4).

When only one operand is staged (the case at 128×128), the same argument gives I = 2MtKt + P(3Kt+1) + 10 and T = 9MtKt + P(13Kt+8) + 10. Table VIII-a compares the formulas with what the simulator actually executed. All 18 predicted values agree exactly with the measurements. This validates the code generator's instruction counts and the simulator's byte and cycle accounting, and it confirms that the staging decisions of Section VI were carried out as intended.

IX. Verification Methodology

Every measurement in Section X is gated on correctness. (1) Oracle: the reference interpreter evaluates the unoptimised Tensor IR in FP32 on the host. It has no tiles, registers or scratchpad and shares no code with the back end. (2) Inputs: never-assigned matrices are filled by a seeded linear congruential generator with values k/8, k ∈ {−16, …, 16}. (3) Four-way testing: mtxverify compiles each program under {baseline, fusion, tiling, fusion+tiling}, runs it, and compares every printed value (relative tolerance 10−5). (4) Negative tests: programs marked expect: error must be rejected with the expected diagnostic text.

Proposition 4 (Exactness of the test arithmetic): For inputs that are multiples of 1/8 in [−2, 2] and contraction length K ≤ 256, every intermediate of a matrix product, bias addition, relu or transpose is exactly representable in FP32. Results are therefore independent of summation order, and fused, tiled and unfused variants agree bit for bit.
Proof: Each product of two inputs is a multiple of 1/64 with magnitude at most 4. Any partial sum of at most K such products is a multiple of 1/64 with magnitude at most 4K ≤ 1024, so it is an integer multiple n/64 with |n| ≤ 65 536 = 216 < 224. Every integer of magnitude below 224 is exact in FP32's 24-bit significand, and scaling by the power of two 2−6 is exact, so each partial sum, and hence each rounding step, is exact. Adding a bias (a multiple of 1/8) keeps the result a multiple of 1/64 within range. Relu and transpose only select or move values. Since no operation rounds, the order of summation is irrelevant.

Programs that apply softmax, or a second layer to already-multiplied values, are not covered by Proposition 4. For softmax, the runtime and the oracle use the same operation order, and the tolerance absorbs any remaining difference. Table IX summarises the test results. B. Findings

F1, super-additivity. On batched_layer, fusion alone gives 1.40× and tiling alone 1.55×, but together they give 2.79×, more than their product (2.17×). Fusion removes the stored and reloaded intermediates, leaving traffic dominated by reads of the broadcast weight tiles. Each of those is reused 32 times (four output row blocks × eight batches), and that is exactly what staging removes.

F2, capacity cliff. Tiling's benefit grows from 2.43× at 32×32 to 3.00× at 64×64 (11× less DRAM traffic), then falls to 1.70× at 128×128. Each 128×128 operand occupies exactly 64 KiB, so only one of the two can be staged. This motivates a second blocking level that stages scratchpad-sized panels [8].

F3, instructions are the wrong metric. Staging adds 11–24% more instructions (e.g. 1,610 → 1,866 on matmul_32), yet cycles fall by 2.4×, because 8-cycle DRAM loads become 1-cycle scratchpad loads.

F4, missing patterns. Fusion gives no gain on attention, whose chain MatMul → ScalarMul → Softmax contains no fusible pair. Scale and online-softmax epilogues [10], [11] are the natural next patterns.

F5, an ISA gap. MROWMAX and MROWSUM reduce one tile, but rows wider than four columns span several tiles. Combining per-tile maxima needs a lane-wise vector maximum, and normalisation needs a row-broadcast divide. Softmax is therefore a runtime call. The compiler pinpoints the minimal ISA extension.

XI. The MatrixDSL Lab

mtxserve is a dependency-free C++ HTTP server bound to 127.0.0.1 that exposes the pipeline as a JSON API (/api/run, /api/suite, /api/programs). A browser dashboard and a Manifest V3 Chrome extension (Fig. 6) send programs to it. They display the traditional and optimised compilations side by side as cards, an animated race and the simulator's transfer/compute timeline. They also show the Tensor IR before and after the passes and the generated assembly, and they re-run the whole ablation study live. The scalar-core figure in the dashboard is an analytic lower bound of one multiply–accumulate per cycle and is labelled as such.

Design and security. The server is single-threaded and runs the same Pipeline object as the command-line compiler, so the dashboard can never disagree with matrixdslc. It binds only to the loopback interface, rejects request bodies over 1 MiB, refuses paths containing .., and serves static files only from the dashboard directory. The Chrome extension's sole host permission is 127.0.0.1:8765. Timelines with more than 600 runs are bucketed by cycle position before being sent, so a 100,000-instruction program still renders smoothly.

XII. Lessons Learned

Freeze interfaces early, integrate early. Frozen headers let four people work in parallel for two reviews. But every defect in Table X lived in a seam between stages, and none was visible to the per-stage tests. Running whole programs end to end found all four within the first integration build.

An oracle beats a long list of expected outputs. Hand-computing expected values for a 128×128 product is impractical. An independent interpreter, combined with inputs chosen so that the arithmetic is exact (Proposition 4), turned every program into a test, including programs written after the oracle.

Let the compiler decide what the ISA needs. The project's rule since Review 2 has been to grow the ISA only when a pass demonstrably needs it. Phase 3 needed no new instructions, and it identified exactly two (a lane-wise maximum and a row-broadcast divide) that a native softmax would require (F5).

Measure the right quantity. Instruction counts went up when tiling was enabled, while cycles and memory traffic went down sharply (F3). Reporting bytes moved and modelled cycles, and deriving them in closed form (Proposition 5), kept the conclusions honest.

XIII. Limitations and Threats to Validity

  • The cycle model has fixed latencies and no bandwidth contention. Runtime calls are charged at a fixed per-element rate, so conclusions concern relative costs only.
  • Code is generated straight-line (fully unrolled). Loop overhead is absent in all configurations alike, but code size grows with the problem (≈100 k instructions for matmul_128).
  • One tile size (4×4) and one scratchpad size (64 KiB) were studied. The cliff in F2 moves with the scratchpad size.
  • Inputs are synthetic. Correctness does not depend on the values, and the model's cycle and byte counts do not depend on them at all.
  • MDT exists as a specification, assembler and simulator, not as hardware.

XIV. Conclusion and Future Work

MatrixDSL shows that the central ideas of production tensor compilers can be co-designed with a target ISA, implemented end to end, verified by an oracle, and measured, within a single course project. Keeping matrix operations whole until target-specific decisions are made enabled fusion and scratchpad staging that together cut modelled cycles by 2.19× and DRAM traffic by 3.79×. Proofs of the rewrites, differential testing and the browser laboratory let every result be checked and reproduced. Future work is second-level blocking to remove the capacity cliff, scale and softmax epilogues, the two-instruction ISA extension for native softmax, loop generation instead of full unrolling, and lowering of the emitted @mdt.* intrinsics through the LLVM TableGen back end.
